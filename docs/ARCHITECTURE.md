# 架构设计

本文说明 A股棱镜 的整体架构、数据链路与关键设计决策。

---

## 1. 设计目标

一个价值投资研究平台要解决的核心矛盾是：**深度分析的「慢」与个人投资者的「快」之间的冲突。**

读一份完整财报、拆三年财务、算一遍 DCF，人工需要数小时；市场机会稍纵即逝。所以本项目的设计目标是：

> 让「接近专业水准的基本面研究」在几分钟内完成，同时保证结论可被复核。

三个具体约束决定了整体架构：

1. **准确性优先于覆盖面** —— 数据缺失时如实展示为空，不用默认值填充
2. **结论必须可验证** —— 每份研报的判断落库，事后自动回填真实表现
3. **可自托管** —— 不依赖任何闭源 SaaS，私有化部署即可运行

## 2. 分层结构

```
┌──────────────────────────────────────────────┐
│  展示层templates/ (Jinja2) + static/          │
│  服务端渲染 · 无前端构建                        │
└───────────────────┬──────────────────────────┘
                    │
┌───────────────────▼──────────────────────────┐
│  应用层  main.py / routers/                    │
│  路由 · 配额校验 · 流式响应 · 生命周期管理       │
└───────────────────┬──────────────────────────┘
                    │
┌───────────────────▼──────────────────────────┐
│  服务层  ai_service / stock_detail_service /   │
│          data_service / dataservice/          │
│  AI 调用编排 · 数据聚合 · 业务计算              │
└──────┬────────────────────────┬─────────────┘
       │                        │
┌──────▼─────────┐    ┌─────────▼─────────────┐
│  数据访问层 db │    │  外部数据源适配          │
│  MySQL / SQLite│    │  data_source / lixinger │
│  连接池 · 行序列化│   │  fuyao_client / datahub │
└─────────────────┘    └───────────────────────┘
```

### 为什么服务端渲染，不用 React

Vue/React SPA 在这个场景下收益为负：

- 研报页面是**长文 + 表格 + K 线**，SEO 要求服务端输出可索引内容，SPA 需要额外做 SSR
- 引入构建链意味着 27 个模板要重写，收益却只体现在交互细节
- 多一层 Node 运行时，1.6G 内存的部署机器扛不住

Bootstrap 5 + 原生 JS 足以支撑当前全部交互，PDF 导出也能直接复用服务端渲染结果。

## 3. 数据面板流水线

这是整个系统最复杂的部分。

```
用户输入股票名/代码
      │
      ├─► 股票解析（本地 stocks 表优先，外部源兜底）
      │
      ▼
按投资偏好选择数据组 picked
      │
      ├─► 并行提交数据任务（ThreadPoolExecutor）
      │     quote / technical / moneyflow / valuation /
      │     profitability / growth / dividend / holder ...
      │
      ▼
  final_data 合并（多源去重、字段兜底、派生指标计算）
      │
      ├─► _format_panel()    → 面板文本（喂给大模型）
      ├─► _panel_metrics_... → 结构化客观指标（回测台账）
      └─► panel_completeness() → 完整度统计（前端展示）
      │
      ▼
  DATA_CACHE（TTL 缓存，key 带组签名）
```

### 三个关键设计

**① 按需组合数据组**

不同投资偏好需要的字段完全不同：

| 偏好 | 侧重 |
|---|---|
| 长线价值 | 多年财务、分红、行业对比 |
| 综合 | 均衡组合 |
| 深度价值 | 现金流、资产负债、估值分位 |

全量拉取会让单次分析从 20 秒变成 3 分钟，且多数数据被浪费。系统按偏好动态提交任务，短线不吃多年财务的等待。

**② 完整度如实暴露**

数据源限流会导致某些字段取不到。传统做法是静默跳过 —— 用户看到一份缺项的报告，却以为是模型写得不好。

本系统会统计每个数据组的完整度并展示，低完整度时给出明确提示。**缺数据要说出来，这是产品可信度的基础。**

**③ 缓存与文本同源**

完整度、客观指标、面板文本必须一起缓存。若只缓存文本，命中缓存时拿不到完整度，页面会显示「—」而面板其实是满的 —— 这类「两处口径分叉」是本项目历史上反复出现的问题。

## 4. AI 调用链路

```
请求进入
   │
   ├─► 配额校验（三通道：每日 / 月度体验 / 赠送）
   ├─► 并发锁（per-user，TTL 300 秒，token 校验）
   │
   ▼
并行启动：数据面板构建 + 大模型流式输出
   │
   ├─► _ThinkFilter      剥离 <think></think> 思考块
   ├─► _EnglishThinkFilter  剥离无标签的裸英文思考
   ├─► 长度预算控制      按偏好分配篇幅区间
   │
   ▼
落库前最终校验 _final_report_problem()
   │  残缺 → 退配额 + 不写台账 + 报明确错误
   ▼
后处理 report_postprocess.inject_compliance
   │  头部 AI 标识 + 尾部免责 + 署名规范化
   ▼
analysis_records + analysis_valuation 双表落库
```

### 两个容易踩的坑

**① 模型可能输出无标签的思考内容**

部分模型（实测 DeepSeek V4 Pro）不遵守 `<think>` 指令，会把整段英文推理直接写进正文，还会带上另一组自相矛盾的估值数字。

防护方式是**段落级检测**：识别「英文词数明显超过汉字数」且「命中 Let me / Hmm / Actually 等思考句式」的段落，予以剔除。阈值需要实测校准 —— 首次上线的判据（英文词数 ≥ 10）在「Base case computed: per share 12.18元」这类短段上会漏网。

**② 报告残缺必须拦截**

模型可能在生成中途被截断，产出只有标题没有内容的「半份研报」。这类残缺报告如果落库，会污染回测台账并消耗用户配额。

校验不通过时**必须退配额** —— 用户没得到完整服务，就不该扣他的次数。

## 5. 回测闭环

这是本项目区别于同类工具的核心设计。

```
   研报生成
      │
      ├─► analysis_records      研报全文
      └─► analysis_valuation   判断台账
             │  score / verdict / val_low / val_mid / val_high
             │  price_at / mc_at / pe_at / pb_at
             │  model / confidence / panel_text（可复现）
             │
             │  每工作日 15:40 自动执行
             ▼
      backfill_valuation
             │  按 horizon 分别到期：
             │  20 日 → 45 天，60 日 → 105 天
             │  120 日 → 180 天，250 日 → 395 天
             ▼
      回填 px_20d / ret_20d ...
             │
             ▼
      /valuation 页面公开对账
        · 模型准确率对比
        · 方向命中率
        · 评分有效性（高分档是否真的涨得好）
```

### 关键设计：按 horizon 分别到期

早期实现是「分析日满 90 天才处理」，导致 `ret_20d` 空置两个月。实际上 20 个交易日 ≈ 30 个自然日，早已可以回填。

改为各 horizon 独立判断后，样本成熟速度提升 3 倍。

### 观察期状态

刚分析的票没有任何收益数据。如果页面只显示已回填的，新用户打开会是空白。

因此每条记录都带**观察进度**（已过天数 / 45 天），让页面在样本积累期依然有内容。

## 6. 告警引擎

守护线程每 5 分钟探活，**交易时段内每小时评估一次**。

```
list_all_enabled_alerts()
      │
      ├─► disclosure 通道 → 读本地披露计划表（零外部请求）
      │
      └─► 行情类指标 → 按股票去重批量拉取
            │
            ├─► 行情类：total_mv / price / pct_chg / pe_ttm / pb / pb_y5
            │     值来自理杏仁，与页面展示同源
            │
            └─► 本地类：val_low（研报合理市值下限）
                  值来自用户自己的 analysis_valuation
```

### 单位陷阱

历史事故：市值提醒的阈值单位是「亿元」，而数据源返回的是「万元」，差 1e4倍。结果「总市值 ≥ 5000 亿」这个条件**恒为真**，所有 ≥ 类规则全部误触发，≤ 类规则永不触发 —— 功能形同虚设。

现在所有指标的取值函数里都写明了单位换算，且与前端 `METRIC_UNITS` 保持一致。

### 本地指标的独有价值

`val_low`（跌破研报合理价）不需要用户填阈值，也不需要额外请求 —— 数值本来就存在用户自己的研报台账里。

⚠️ 实现时必须**按 (user_id, ts_code) 取值**，不能放进 `(ts_code, metric)` 的共享缓存：同一只票，不同用户的研报结论可能完全相反。

## 7. 前端设计系统

三份 CSS 分层加载，职责严格分离：

| 文件 | 职责 | 加载位置 |
|---|---|---|
| `tokens.css` | 设计令牌（纯变量，零副作用） | 最前 |
| `responsive.css` | 移动端统一适配（覆盖 27 个模板的内联样式） | 中间 |
| `vision.css` | 视觉增强（质感、排版、焦点态、滚动条） | 最后 |

### 令牌层不写任何选择器规则

这是刻意的：令牌文件只声明变量，**不会覆盖任何现有样式**。同时通过「兼容别名」把历史散落的变量名（`--bg-card`、`--text-main` 等）接到新体系，让既有模板无需改动即可受益。

### 视觉概念：深空观测台

深邃夜空做底，品牌蓝紫当极光，玻璃质感做仪表盘，**等宽数字**做金融终端的精密感。科技感来自「精密」，不是来自发光。

关键手法：

- 全局 `font-variant-numeric: tabular-nums` —— 金融表格数字不对齐，整页专业感就崩了
- 星尘噪点用内联 SVG data-uri，零网络请求
- 毛玻璃只给导航与弹窗，**不给卡片网格**（否则整屏模糊层在低端机上掉帧）
- `prefers-reduced-motion` 全局尊重

## 8. 隐私与安全

| 项目 | 措施 |
|---|---|
| 密码存储 | PBKDF2-HMAC-SHA256，10 万次迭代，16 字节随机盐 |
| 会话 | HTTP-only Cookie，密钥从环境变量读取 |
| 限流 | 游客与登录用户分级，per-IP 与 per-user 分离 |
| 并发 | per-user 分析锁，TTL 300 秒 + token 校验 |
| 密钥 | 全部走环境变量，仓库内只有 `.env.example` |
| SQL | 全部参数化查询 |

### 代理绕过

宿主机常会注入 `http_proxy` 环境变量，服务进程继承后，所有外部请求会绕道代理；宿主退出后端口无人监听，导致**全部外部请求失败**且报错只说「连接失败」，指不到根因。

启动时注入 `NO_PROXY` 白名单（国内数据源 + 国内 AI 渠道 + 本机），境外 API 仍走代理。**境外源直连会长时间挂起，代理不可达至少能快速失败** —— 这是刻意选择的失败模式。

## 9. 后台任务

| 任务 | 频率 | 说明 |
|---|---|---|
| `_valuation_backfill_worker` | 工作日 15:40 | 研报走势回填 |
| `_market_cache_warmer` | 每 25 秒 | 大盘缓存保温（TTL 30 秒） |
| 提醒评估守护线程 | 交易时段每小时 | 告警规则判定 |
| 热门榜单 | 交易时段每小时 | 龙虎榜与题材榜 |
| 披露日历同步 | 每 6 小时 | 财报预约披露计划 |

⚠️ 1.6G 内存的部署环境下，后台任务的并发数必须严格控制 —— 曾因一次记忆元凶排查发现旧版服务进程仍在占用 39.5MB 内存。
